## 1. 问题描述

### 1.1 问题场景

车辆上传包含动力电池电压数据、整车电压/电流或驱动电机数据时，SDK 需要按
GB/T 32960-2016 的字段顺序、倍率和偏移量生成业务模型；合法的终端帧还应只在
解密、结构解码和认证成功后收到 `SUCCESS` 应答。

### 1.2 具体表现

- 动力电池子系统总电压会被当作单体数，合法帧随后读取越界。
- 整车/电机电压、电流和电机转速被错误换算，输出可高出 10 倍或偏移 20,000 rpm。
- 加密校时应答携带加密标志却发送明文；格式错误帧会先收到 `SUCCESS`。
- Spring 应用无法可靠覆盖 SDK 的默认认证与回调 Bean。

### 1.3 错误信息

修改期间的回归失败证明了电流偏移量不能沿用旧夹具：

```
VehicleSimulatorTest.shouldHandleBatteryData
expected: <-20.0> but was: <880.0>
```

## 2. 根本原因分析

### 2.1 问题分析过程

1. 逐字段比对协议的倍率、偏移量与电池电压数据布局。
2. 发现 `decodeBatteryVoltageData` 将子系统编号后的 WORD 直接读为单体数，遗漏了
   总电压、总电流、总单体数和本帧定位字段。
3. 检查测试夹具后发现它复制了同一简化布局，无法发现生产解码错误。
4. 跟踪收包路径后发现自动 `SUCCESS` 在解密与类型解码之前发送。
5. 检查出站路径后确认 `CryptoProvider.encrypt` 没有调用点。

### 2.2 直接原因

- `gb32960-core/src/main/java/io/github/im10furry/gb32960/core/codec/MessageDecoder.java:233-259`
  使用了错误的倍率或偏移量。
- `MessageDecoder.java:351-370` 未实现动力电池电压的完整布局。
- `gb32960-transport/src/main/java/io/github/im10furry/gb32960/transport/handler/MessageHandler.java:74-99`
  现已调整为先处理、后成功应答。

### 2.3 根本原因

实现与测试共享自定义报文构造器，没有独立的协议向量；加密能力只有 Provider 实现，
没有覆盖到编码和自动应答路径。模型字段也没有承载完整的电池子系统语义。

### 2.4 为什么没有提前发现

已有测试主要验证编解码自洽，未覆盖真实字段顺序、非零电流偏移、加密出站和
“解码失败不得成功确认”的端到端场景。

## 3. 解决方案

- 以协议布局扩充 `BatteryVoltageData.Subsystem`，并保留废弃的 `cellCount` 访问器以减小
  调用方源码兼容风险。
- 修正整车/电机/电池子系统的 `0.1`、`0.001` 倍率与 `1000A`、`20000rpm` 偏移。
- 解析车辆登录中的电池系统编码，并将缓冲区下溢转换为领域 `DecodeException`。
- 出站响应接受 `CryptoProvider`，在计算帧长度和 BCC 前加密 data unit。
- 收包顺序调整为解密、解码、认证、应答、回调；失败路径返回 `ERROR`。
- 默认认证和回调 Bean 改为可覆盖；异步回调执行器改为有界线程池与队列。

## 4. 影响范围评估

`BatteryVoltageData.Subsystem` 新增字段；原有 `getCellCount()` 仍存在但已标记废弃。
修正后的物理量是行为变更，使用历史错误倍率的下游消费者应在发布说明中迁移。

## 5. 预防措施

### 5.1 代码层面

- [x] 可变长协议体统一将缓冲区下溢转换为可诊断的解码错误。
- [x] 加密报文必须在编码路径实际调用 `CryptoProvider`。
- [x] 自动成功应答只能发生在结构和认证通过之后。

### 5.2 测试层面

- [x] 增加真实电池电压字段布局、加密响应和错误应答测试。
- [ ] 引入来自真实终端/平台的脱敏 golden vectors，并在 CI 中逐字节校验。

### 5.3 流程层面

- [ ] 每次协议字段变更同时审查模型、编解码器、报文夹具、集成测试与发布说明。

## 6. 经验总结

> 二进制协议的测试必须以独立的真实字节向量为准；与实现共享的构造器只能验证自洽，不能证明互通。
